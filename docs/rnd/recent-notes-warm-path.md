# Recent Notes Warm Path

_Status: active_
_Started: 2026-06-04 - Decided: _

## Hypothesis

`get_recent_notes` is a common "what changed?" entry point and is referenced by
workflow prompts to avoid per-note fan-out. It currently walks the note list and
stats every note on each call. Reusing safe vault-root resolution or a small
mtime inventory may cut the 1,000-note warm call by at least 20% without
changing ordering, `since` filtering, folder filtering, displayed paths, or
vault-boundary checks.

## Fixture

Bench command:

```powershell
npm run build
node scripts\bench-recent-notes.mjs 100,1000 --json
```

The harness creates temporary vaults with 100 or 1,000 markdown notes. Notes are
spread across `journal/` and nested `projects/area-*` folders, have deterministic
hour-spaced mtimes, and contain small tag-bearing bodies. It calls
`get_recent_notes` twice without filters, then once with `since: "7d"` through a
real stdio MCP client.

Baseline captured on 2026-06-04 from the slower of two sequential runs:

| notes | cold get_recent_notes | warm get_recent_notes | warm get_recent_notes since=7d |
|---:|---:|---:|---:|
| 100 | 22.3ms | 15.7ms | 24.5ms |
| 1,000 | 125.0ms | 107.1ms | 113.7ms |

## Metric

Primary metric: 1,000-note warm `get_recent_notes` wall time.

Ship bar: warm `get_recent_notes` at or below 86ms (20% faster than the
107.1ms baseline), with 1,000-note cold `get_recent_notes` no worse than 138ms
and warm `since: "7d"` no worse than 125ms. Result count, sort order, ISO mtime
rendering, `since` filtering, folder filtering, and escaped displayed paths must
stay unchanged.

| | before | after |
|---|---:|---:|
| 1,000-note warm get_recent_notes | 107.1ms | |
| 1,000-note cold get_recent_notes guardrail | 125.0ms | |
| 1,000-note warm get_recent_notes since=7d guardrail | 113.7ms | |

## Safety review

Data accessed: synthetic temporary markdown vaults generated by
`scripts/bench-recent-notes.mjs`. No real vault content, secrets, network calls,
or embedding providers are involved.

Writes performed: temporary fixture vault creation and deletion only. A future
prototype may add in-memory mtime metadata; it must preserve vault-boundary
checks, per-note stat freshness, folder filtering, and the raw note content
contract.

Logs emitted: normal stdio server startup logs with temporary vault paths. No
note body content is logged.

Rollback path: drop the prototype and keep direct per-call note stat scanning.

## Kill criterion

Stop if the warm call improves by less than 20%, if cold or `since` guardrails
are exceeded, if note ordering changes after mtime edits, or if the
implementation needs a persistent index or filesystem watcher to stay correct.
