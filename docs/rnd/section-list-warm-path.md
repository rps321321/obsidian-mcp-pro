# Section List Warm Path

_Status: shipped_
_Started: 2026-06-04 - Decided: 2026-06-04_

## Hypothesis

`list_sections` is the discovery step before targeted `get_note`, `update_section`,
and `insert_at_section` calls. It currently reads the whole note and parses every
heading on each call. A measured heading-list path may cut repeated calls on
heading-heavy notes by at least 20% without changing heading order, indentation,
control-character escaping, path validation, or no-heading errors.

## Fixture

Bench command:

```powershell
npm run build
node scripts\bench-sections.mjs 100,1000 --json
```

The harness creates temporary vaults with one markdown note containing 100 or
1,000 generated headings spread across levels 1-4, with short body paragraphs
between headings. It calls `list_sections` twice through a real stdio MCP
client.

Baseline captured on 2026-06-04 from the slower values across two sequential
runs:

| headings | cold list_sections | warm list_sections |
|---:|---:|---:|
| 100 | 5.8ms | 1.8ms |
| 1,000 | 5.9ms | 3.2ms |

## Metric

Primary metric: 1,000-heading warm `list_sections` wall time.

Ship bar: warm `list_sections` at or below 2.6ms (20% faster than the 3.2ms
baseline), with 1,000-heading cold `list_sections` no worse than 6.5ms.
Heading count, rendered order, indentation by heading level, escaped displayed
heading text, and missing-note/no-heading behavior must stay unchanged.

| | before | after |
|---|---:|---:|
| 1,000-heading warm list_sections | 3.2ms | 1.4ms / 1.2ms |
| 1,000-heading cold list_sections guardrail | 5.9ms | 5.6ms / 5.6ms |

## Safety review

Data accessed: synthetic temporary markdown vaults generated by
`scripts/bench-sections.mjs`. No real vault content, secrets, network calls, or
embedding providers are involved.

Writes performed: temporary fixture vault creation and deletion only.

Logs emitted: normal stdio server startup logs with temporary vault paths. No
note body content is logged.

Rollback path: drop any prototype and keep direct full-file reads followed by
`parseHeadings`.

## Kill criterion

Stop if the warm call improves by less than 20%, if the cold guardrail is
exceeded, if heading rendering changes, or if the implementation needs a
persistent index or filesystem watcher to stay correct.

## Decision

Ship. `list_sections` now renders through a small cache keyed by vault path and
note path, and reuses the rendered heading list only when the current resolved
path, size, and mtime match. Cache misses read the already-validated full path
directly, preserving the vault-boundary check while avoiding duplicate path
resolution. Section write tools invalidate the cached heading list after
successful same-process edits.

A regression test warms `list_sections`, edits a same-size heading through
`replace_in_note`, and verifies the next heading list reflects the new heading.

Measured after the prototype with:

```powershell
npm run build
node scripts\bench-sections.mjs 100,1000 --json
node scripts\bench-sections.mjs 100,1000 --json
```

The repeated 1,000-heading warm calls were 1.4ms and 1.2ms, both below the
2.6ms ship bar. Cold calls were 5.6ms and 5.6ms, below the 6.5ms guardrail.
