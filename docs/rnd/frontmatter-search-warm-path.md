# Frontmatter Search Warm Path

_Status: shipped_
_Started: 2026-06-04 - Decided: 2026-06-04_

## Hypothesis

`search_by_frontmatter` is a common metadata workflow for status, type, owner,
and tag-like properties. It still reads every candidate note directly and parses
frontmatter on each call, so repeated metadata lookups pay the full vault scan
again. Reusing warm note bodies or derived frontmatter metadata should cut the
1,000-note warm call by at least 20% without changing scalar matching,
array-valued matching, folder filtering, truncation, displayed frontmatter, or
read-failure handling.

## Fixture

Bench command:

```powershell
npm run build
node scripts\bench-frontmatter-search.mjs 100,1000 --json
```

The harness creates temporary vaults with 100 or 1,000 markdown notes. Notes are
spread across `archive/` and nested `projects/team-*` folders, include
frontmatter keys for `status`, `type`, `priority`, `owner`, and `tags`, and have
one sparse `status: ready-to-ship` target at the final note. It calls
`search_by_frontmatter` twice for the whole vault, then once with
`folder: "projects"` through a real stdio MCP client.

Baseline captured on 2026-06-04 from the slower 1,000-note values across two
sequential runs:

| notes | cold search_by_frontmatter | warm search_by_frontmatter | warm search_by_frontmatter folder=projects |
|---:|---:|---:|---:|
| 100 | 20.4ms | 15.1ms | 12.8ms |
| 1,000 | 104.0ms | 93.1ms | 66.2ms |

## Metric

Primary metric: 1,000-note warm `search_by_frontmatter` wall time.

Ship bar: warm `search_by_frontmatter` at or below 74ms (20% faster than the
93.1ms baseline), with 1,000-note cold `search_by_frontmatter` no worse than
115ms and warm folder-scoped `search_by_frontmatter` no worse than 73ms.
Matching rows, `maxResults` truncation, scalar and array comparison, folder
scope, displayed frontmatter, and escaping must stay unchanged.

| | before | after |
|---|---:|---:|
| 1,000-note warm search_by_frontmatter | 93.1ms | 30.8ms / 30.8ms |
| 1,000-note cold search_by_frontmatter guardrail | 104.0ms | 73.2ms / 68.1ms |
| 1,000-note warm search_by_frontmatter folder=projects guardrail | 66.2ms | 25.7ms / 28.5ms |

## Safety review

Data accessed: synthetic temporary markdown vaults generated by
`scripts/bench-frontmatter-search.mjs`. No real vault content, secrets, network
calls, or embedding providers are involved.

Writes performed: temporary fixture vault creation and deletion only. The
prototype routes candidate note reads through the shared content cache; it
preserves vault-boundary checks, mtime invalidation, folder filtering,
frontmatter parse behavior, and raw note content behavior.

Logs emitted: normal stdio server startup logs with temporary vault paths. No
note body content is logged.

Rollback path: drop the prototype and keep direct per-call frontmatter scanning.

## Kill criterion

Stop if the warm call improves by less than 20%, if cold or folder guardrails
are exceeded, if scalar or array-valued matching changes, if stale frontmatter
can be returned after an edit, or if the implementation needs a persistent index
or filesystem watcher to stay correct.

## Decision

Ship. `search_by_frontmatter` now reads candidate note bodies through
`readAllCached` instead of calling `readNote` once per path. Repeat metadata
lookups reuse warm note bodies while the cache still stats paths and invalidates
edited notes. A regression test warms a missing frontmatter lookup, writes a
note with the matching property, and verifies the next lookup returns it.

Measured after the prototype with:

```powershell
npm run build
node scripts\bench-frontmatter-search.mjs 100,1000 --json
node scripts\bench-frontmatter-search.mjs 100,1000 --json
```

The repeated 1,000-note warm calls were 30.8ms and 30.8ms, both below the 74ms
ship bar. Cold calls were 73.2ms and 68.1ms, below the 115ms guardrail, and
warm folder-scoped calls were 25.7ms and 28.5ms, below the 73ms guardrail.
