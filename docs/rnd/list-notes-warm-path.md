# List Notes Warm Path

_Status: stopped_
_Started: 2026-06-04 - Decided: 2026-06-04_

## Hypothesis

`list_notes` is a common first step for browsing a vault or selecting batch
targets. It is already fast on the synthetic fixture, but repeated whole-vault
listings still pay traversal and response-rendering work. A small warm-path
improvement should cut the 1,000-note warm listing by at least 20% without
changing folder filtering, sort order, limit handling, total-count reporting,
displayed paths, or vault-boundary checks.

## Fixture

Bench command:

```powershell
npm run build
node scripts\bench-list-notes.mjs 100,1000 --json
```

The harness creates temporary vaults with 100 or 1,000 markdown notes spread
across `reference/` and nested `projects/team-*` folders. It calls `list_notes`
through a real stdio MCP client with `limit: 10000` for a cold whole-vault list,
a warm whole-vault list, and a warm folder-scoped list for `projects/team-7`.

Baseline captured on 2026-06-04 from the slower 1,000-note values across two
sequential runs:

| notes | cold list_notes | warm list_notes | warm folder list_notes |
|---:|---:|---:|---:|
| 100 | 8.0ms | 3.6ms | 1.6ms |
| 1,000 | 15.8ms | 10.9ms | 3.1ms |

## Metric

Primary metric: 1,000-note warm `list_notes` wall time for a whole-vault list
with `limit: 10000`.

Ship bar: warm whole-vault listing at or below 8.7ms (20% faster than the 10.9ms
baseline), with 1,000-note cold listing no worse than 17ms and warm folder
listing no worse than 4ms. Folder filtering, result ordering, count text, limit
truncation, escaping, and path validation must stay unchanged.

| | before | after |
|---|---:|---:|
| 1,000-note warm list_notes | 10.9ms | 10.4ms |
| 1,000-note cold list_notes guardrail | 15.8ms | 13.8ms |
| 1,000-note warm folder list_notes guardrail | 3.1ms | 3.9ms |

## Safety review

Data accessed: synthetic temporary markdown vaults generated by
`scripts/bench-list-notes.mjs`. No real vault content, secrets, network calls, or
embedding providers are involved.

Writes performed: temporary fixture vault creation and deletion only. A future
prototype may cache rendered note lists or reuse traversal metadata, but it must
preserve excluded directory handling, symlink skipping, permission checks, folder
validation, and stale file-set detection.

Logs emitted: normal stdio server startup logs with temporary vault paths. No
note body content is logged.

Rollback path: drop the prototype and keep direct `listNotes` rendering.

## Kill criterion

Stop if the warm call improves by less than 20%, if cold or folder guardrails
are exceeded, if list order/count/truncation changes, if stale file additions or
deletions can survive in warm output, or if the implementation needs a persistent
index or filesystem watcher to stay correct.

## Decision

Stopped. A rendered-response cache that still re-ran the safe `listNotes` walk
for freshness measured 8.7ms on the first 1,000-note warm run but 10.4ms on the
repeat, missing the 8.7ms ship bar. Cold and folder-scoped guardrails stayed
under their limits, but the primary metric did not hold.

No runtime change ships. The listing path is already fast enough that a safe
warm improvement probably needs a broader freshness strategy shared with other
vault file inventories, not a `list_notes`-only render cache.
