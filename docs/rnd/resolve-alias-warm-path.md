# Resolve Alias Warm Path

_Status: shipped_
_Started: 2026-06-04 - Decided: 2026-06-04_

## Hypothesis

`resolve_alias` translates human-friendly names to Obsidian note paths and is
used before note reads in assistant workflows. It currently reads and parses
frontmatter for every note on every call, so repeated alias lookups and basename
fallbacks still scan the vault. A small alias inventory or use of the shared
content cache should cut the 1,000-note warm call by at least 20% without
changing alias matching, basename fallback, output grouping, path escaping, or
per-note read-failure behavior.

## Fixture

Bench command:

```powershell
npm run build
node scripts\bench-resolve-alias.mjs 100,1000 --json
```

The harness creates temporary vaults with 100 or 1,000 markdown notes. Notes are
spread across `projects/` and nested `people/team-*` folders, each note has
frontmatter aliases, and the last note carries the target alias `project atlas`.
It calls `resolve_alias` twice for that alias, then once for the last note's
basename through a real stdio MCP client.

Baseline captured on 2026-06-04 from the slower 1,000-note values across two
sequential runs:

| notes | cold resolve_alias | warm resolve_alias | warm resolve_alias basename |
|---:|---:|---:|---:|
| 100 | 20.9ms | 13.4ms | 10.8ms |
| 1,000 | 125.7ms | 86.6ms | 86.2ms |

## Metric

Primary metric: 1,000-note warm `resolve_alias` wall time.

Ship bar: warm `resolve_alias` at or below 69ms (20% faster than the 86.6ms
baseline), with 1,000-note cold `resolve_alias` no worse than 138ms and warm
basename fallback no worse than 95ms. Alias matches, basename matches, ordering,
error handling, and displayed path escaping must stay unchanged.

| | before | after |
|---|---:|---:|
| 1,000-note warm resolve_alias | 86.6ms | 40.5ms / 62.8ms |
| 1,000-note cold resolve_alias guardrail | 125.7ms | 76.9ms / 118.0ms |
| 1,000-note warm resolve_alias basename guardrail | 86.2ms | 34.0ms / 51.7ms |

## Safety review

Data accessed: synthetic temporary markdown vaults generated by
`scripts/bench-resolve-alias.mjs`. No real vault content, secrets, network
calls, or embedding providers are involved.

Writes performed: temporary fixture vault creation and deletion only. The
prototype routes alias reads through the shared content cache; it preserves
vault-boundary checks, cache invalidation, basename fallback, and raw note
content behavior.

Logs emitted: normal stdio server startup logs with temporary vault paths. No
note body content is logged.

Rollback path: drop the prototype and keep direct per-call frontmatter scanning.

## Kill criterion

Stop if the warm alias lookup improves by less than 20%, if cold or basename
guardrails are exceeded, if edits to aliases are stale on the next call, or if
the implementation needs a persistent index or filesystem watcher to stay
correct.

## Decision

Ship. `resolve_alias` now reads note bodies through `readAllCached` instead of
calling `readNote` once per path. Repeat lookups reuse warm note bodies while
the cache still stats paths and invalidates edited notes. A regression test
warms a missing alias lookup, writes a note with that alias, and verifies the
next lookup returns the new match.

Measured after the prototype with:

```powershell
npm run build
node scripts\bench-resolve-alias.mjs 100,1000 --json
node scripts\bench-resolve-alias.mjs 100,1000 --json
```

The repeated 1,000-note warm alias calls were 40.5ms and 62.8ms, both below the
69ms ship bar. Cold calls were 76.9ms and 118.0ms, below the 138ms guardrail,
and warm basename fallback calls were 34.0ms and 51.7ms, below the 95ms
guardrail.
