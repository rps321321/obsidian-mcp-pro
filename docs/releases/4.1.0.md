# obsidian-mcp-pro 4.1.0 release notes

Published on 2026-10-23 as [npm 4.1.0](https://www.npmjs.com/package/obsidian-mcp-pro/v/4.1.0), with matching [GitHub release and tag](https://github.com/rps321321/obsidian-mcp-pro/releases/tag/v4.1.0) at commit `3c21b285d78b03f1e64e51a27036d17ee2a81a63`. The downloaded registry tarball matches the tested candidate byte for byte, with SHA-256 `ba7707923e3fdd52bf68d7c3a5acfd624a9689bf189c24425932115eb2589d45`.

## Consumer SDK requirement

The configured input budget requires SDK 1.32.1 or newer. Version 4.1.0 declared `^1.29.0`, so an existing consumer lockfile can retain an SDK that silently ignores that option. A bounded installed-package reproduction confirmed dispatch above the intended budget with SDK 1.29.0. A passing repository audit or fresh dependency resolution does not establish enforcement in a retained consumer graph.

The correction is published as [npm 4.1.1](https://www.npmjs.com/package/obsidian-mcp-pro/v/4.1.1) on 2026-10-23, with matching [GitHub release and tag](https://github.com/rps321321/obsidian-mcp-pro/releases/tag/v4.1.1) at commit `36a755ca0d1a756cc2f19760e9c31b03ffdd0d68`. The independently downloaded registry tarball has SHA-256 `858851ba031b8933799f4f156ddecd24a768a232736d0d27ec8b07e709be5b2d`. Version 4.1.1 requires SDK `^1.32.1` and adds an installed-consumer regression with an intentionally retained old root SDK. See [dependency security](../dependency-security.md#consumer-sdk-resolution-correction-in-411) for the exact evidence. Applications using 4.1.0 must ensure their resolved core SDK is at least 1.32.1. This does not make a separately pinned old SDK elsewhere in the application safe.

## Changes in 4.1.0

- HTTP Roles register only the explicit Tool snapshot and permitted resources and prompts. Tokens are bound to sessions; permission changes close affected sessions. Legacy single-token embedding and full-catalog stdio remain supported.
- `HttpServerOptions.allowedHosts` configures additional destination Host values while retaining derived defaults and DNS-rebinding protection. IPv6 URL and derived Host spelling is canonical.
- `createMcpServerServices(vaultPath)` and `buildMcpServer` service injection let HTTP sessions share vault services without sharing authorization.
- Explicit vault selection, canonical exclusions, YAML error sanitization, confirmation failures, note-move links, cache signatures and HTTP startup cleanup received correctness fixes.
- Note replacement preserves POSIX modes and rejects observed competing edits. Conflict detection is optimistic, not an atomic compare-and-swap.
- Regex replacement uses a terminable worker with a deadline and output limit. Heap settings do not guarantee an aggregate process-memory bound.

See the [changelog](../../CHANGELOG.md) for the full list. Node.js remains `>=24.0.0`. Tool names and supported schemas remain compatible with 4.x; the input budget restricts extra argument structure. Roles grant whole Tools and their side effects, not per-token folder isolation. Already executing operations are not rolled back by revocation.

## Published attachment behavior

The 4.0.1 npm tarball already returned images as MCP `image` blocks, audio as `audio` blocks and other binaries as base64 `resource` blocks with `vault://` URIs. The matching [release source](https://github.com/rps321321/obsidian-mcp-pro/blob/0d91e1f013339cf9d08b99f3f288b5477ef33816/src/tools/attachments.ts#L637-L670) contains those branches. The [MIME mapping](https://github.com/rps321321/obsidian-mcp-pro/blob/0d91e1f013339cf9d08b99f3f288b5477ef33816/src/lib/mime.ts#L44-L79) assigns PDFs `application/pdf` and unknown extensions, including DOCX, `application/octet-stream`.

The shared Tool-seam migration preserves those bytes and block types and represents SVG as untrusted `text/plain` resource content. It does not prove that the PDF/DOCX rejection in [plugin issue #2](https://github.com/rps321321/obsidian-mcp-pro-plugin/issues/2) is resolved. Keep that issue open until the affected client's conversion or unsupported capability is verified with non-sensitive fixtures. Record the actual server/client versions, transport and raw response, and check unchanged decoded bytes separately from downstream rendering.

## Publication checklist

For each selected release commit:

1. Check package and lockfile root versions and required dependency minimums. Exercise a retained consumer lock as well as a fresh resolution.
2. Review README, CHANGELOG, these notes and SECURITY's support range against the intended version and actual registry state. Update support policy when the supported range changes.
3. Run `npm run verify:full`, inspect the package contents and run the actual installed-consumer probe. Record commit-specific CI and artifact identities. Observe the local release-cadence approval rule.
4. Publish normally so `prepublishOnly` runs. Verify npm metadata, the downloaded tarball and matching GitHub tag/release before marking the version published.
5. Upgrade the companion from the registry artifact, run a clean install and native acceptance, and review/merge that delivery separately. Do not close attachment-client reports from publication alone.
