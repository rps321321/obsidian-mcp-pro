# obsidian-mcp-pro 4.1.0 preparation notes

**Unreleased.** As checked on 2026-10-23, npm's `latest` version and the latest
[GitHub release](https://github.com/rps321321/obsidian-mcp-pro/releases/tag/v4.0.1)
are 4.0.1, published on 2026-06-21. The source package and lockfile declare 4.1.0;
that declaration does not mean the package has been published. No publication
date is set.

## Published attachment behavior

The published 4.0.1 npm tarball already returns images as MCP `image` blocks,
audio as `audio` blocks, and other binaries as base64 `resource` blocks with
`vault://` URIs. Its matching
[release source](https://github.com/rps321321/obsidian-mcp-pro/blob/0d91e1f013339cf9d08b99f3f288b5477ef33816/src/tools/attachments.ts#L637-L670)
contains these branches. The
[MIME mapping](https://github.com/rps321321/obsidian-mcp-pro/blob/0d91e1f013339cf9d08b99f3f288b5477ef33816/src/lib/mime.ts#L44-L79)
assigns PDFs `application/pdf` and unknown extensions, including DOCX,
`application/octet-stream`.

The shared tool-seam migration preserves those binary bytes and block types. It
also represents SVG as untrusted `text/plain` resource content. It is not evidence
that the PDF/DOCX rejection reported in
[plugin issue #2](https://github.com/rps321321/obsidian-mcp-pro-plugin/issues/2)
is resolved. The
[corrected diagnosis](https://github.com/rps321321/obsidian-mcp-pro-plugin/issues/2#issuecomment-6330070208)
requires checking the affected client and its conversion of the MCP response.

## Merged source changes awaiting publication

The following changes are in the source branch. Consult the
[Unreleased changelog](../../CHANGELOG.md#unreleased) for the current list of
fixes; publication and consumer verification remain separate steps.

- All nine tool groups register through `defineTool` and the branded
  `ToolResult` vocabulary. Error sanitization and untrusted-content wrapping are
  centralized, including attachment media constructors.
- The vault module is split into filesystem, note-read, note-operation, search,
  statistics, canvas, and Bases modules. The compatibility barrel retains the
  public API. Point reads remain direct; vault-wide scans use an explicit
  in-memory batch cache. The unused note-cache persistence surface was removed.
- Semantic state has an explicit `EmbeddingStore` owner. The new
  `createMcpServerServices(vaultPath)` API and `buildMcpServer` service injection
  let HTTP session servers share a live embedding-store handle.
- `HttpServerOptions.allowedHosts` lets library callers configure additional
  destination Host values while retaining the default host checks.
- Interactive confirmation fails closed on errors and cancellation. Clients
  without form elicitation retain the explicit-latch fallback. Permanent
  deletion still requires `confirm: true`.

## Compatibility to verify for 4.1.0

- Node.js remains `>=24.0.0`.
- No breaking change to 4.x MCP tool names or schemas is intended.
- Unexpected thrown tool errors use the generic `Error:` prefix documented in
  ADR 0001.
- `get_backlinks` omits the former decorative arrow before wrapped context;
  trust metadata and content remain unchanged.
- The shared-server-service and embedding-store APIs require the unpublished
  source changes above. The companion plugin must adapt and verify its own
  integration before adopting them.

## Publication checklist

Complete these steps against the chosen release commit. This is planned release
work, not a record of completed publication.

1. Confirm the release version and compare `package.json` with the lockfile's
   root metadata. Regenerate the lockfile only if needed.
2. Review README, CHANGELOG, these notes, and SECURITY's supported-version policy
   together against that version and the currently published npm package.
   Update the security support range whenever support changes. Check that README
   examples identify APIs unavailable in the current published package and that
   validation claims link to commit-specific CI results.
3. Complete the outstanding release requirements in
   [dependency security](../dependency-security.md),
   [core issue #311](https://github.com/rps321321/obsidian-mcp-pro/issues/311), and
   [package consumer verification #312](https://github.com/rps321321/obsidian-mcp-pro/issues/312).
   Record the evidence for the exact release commit.
4. Run `npm run verify` and, when applicable, `npm run verify:full`. Inspect
   `npm pack --dry-run`, then test the actual tarball in a fresh consumer for the
   public entry points and CLI behavior required by #312.
5. Publish the approved version. Verify npm metadata, the downloaded tarball,
   and the matching GitHub tag/release before marking these notes released or
   removing README's unreleased API qualifications.
6. Rebuild the companion plugin against the published dependency, adapting its
   service ownership and testing protocol compatibility. Record the installed
   package version and transport. An upgrade alone does not resolve plugin #2.

## Separate attachment-client verification

Keep plugin issue #2 open until the affected client accepts the attachments or
its unsupported capability is accurately documented. Record the actual server
and client versions, launch command, transport, and a non-sensitive PDF/DOCX
fixture. Capture the raw `tools/call` response before client conversion and
verify its block type and unchanged decoded bytes separately from downstream
rendering or conversion. Neither a merged change nor a new package publication
alone satisfies this gate.
